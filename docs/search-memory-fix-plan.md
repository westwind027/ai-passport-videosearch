# ESP32-C3 搜索链路内存根治方案

适用范围：`folo/ai-passport-c3`（ESP32-C3、无 PSRAM、ESP-IDF 5.5.5）。

## 实施状态（2026-09-14）

方案已实现并通过指定工具链与实机验证：

- 14336 B 网络接收区、10240 B JPEG 解码区和 640 B LCD 行缓冲均为固定存储；
- 搜索 JSON 直接进入网络接收区，解析过程不再建立 cJSON 树或 body `std::string`；
- 最多 12 条结果使用约 5.4 KiB 固定容量存储，`VideoSearchClient` 独占结果所有权，
  `SearchSession` 仅保存只读指针；
- 搜索、图片和播放器控制共用一个 8192 B 静态常驻任务；
- 三类 HTTP 操作统一改用 ESP-IDF 同步 HTTP 客户端，在 8192 B 静态 worker 中执行；
- HTTP 每次仅使用 1024 B 内部读缓冲，响应直接写入固定接收区，不再创建
  esp-ml307 `tcp_receive` 任务或动态 body 队列；
- HTTP 打开前检查 4 KiB 最大连续块和 8 KiB 总空闲内部堆；
- 12 条搜索响应超出 14336 B 时按 6、3、1 条有界降级；
- 42 项仓库回归通过；ESP-IDF 5.5.5 规定入口完整构建通过，固件分区仍有 18% 空间；
- 设备连续完成 7 次“ASR -> 搜索 -> 320 像素 JPEG 分块解码 -> 展示”，以及播放器
  打开/关闭控制；最差一次 ASR 结束瞬间最大连续块为 4608 B，音频关闭后 worker 为
  9216 B，仍正常完成请求；未再出现 `search needs more free network memory`、OOM 或重启；
- 连接预热后空闲 SRAM 稳定在约 26.9--27.1 KiB，未观察到线性泄漏。

第 6 节的 50 轮长稳验收仍应保留，但原先导致搜索基本不可用的内存门控和异步接收任务
问题已经由实机回归闭环。

## 1. 目标

搜索链路改为固定工作集：完成初始化后，搜索、图片下载、JPEG 分块解码、翻页和远程播放
不得再申请或释放大块内存。内存不足只能转成有界错误或图片规格降级，不能触发
`std::bad_alloc`、`abort()` 或设备重启。

保持以下产品能力不变：

- 搜索请求默认 `limit=12`；
- 全屏请求小图并旋转 90 度显示；
- JPEG 采用分块解码，不保留 320x240 RGB565 全帧；
- XiaoZhi ASR、Wi-Fi 配置、设置菜单继续工作；
- 构建环境固定为 ESP-IDF `5.5.5`。

## 2. 已确认根因

连续复现时，图片 HTTP 已正常结束，随后出现：

```text
worker op=3 start: heap free=42064 largest=10752
Failed to allocate reusable search image decode buffer
heap free=42020 largest=10752
```

当前解码区通过 `heap_caps_aligned_alloc(16, 10752, ...)` 申请。最大连续块虽然也是
10752 字节，但对齐和分配器元数据仍需额外空间，所以该申请确定性失败。重试 20 次不能
改变已经碎片化的堆布局。

直接原因是当前实现为了给 TCP 连接腾出空间，会释放已经预分配的解码区；HTTP 关闭后
再尝试申请回来。搜索响应还使用动态 `std::string`、`std::vector`、结果字段字符串和
cJSON 节点，进一步切碎内部堆。第三方 esp-ml307 TCP 接收任务也会动态创建任务栈和
body chunk，其任务内未捕获的 `std::bad_alloc` 会直接终止设备。

因此，继续增加缓冲、等待重试或调整错误提示都不能消除根因。

## 3. 目标模块

`VideoSearchClient` 作为搜索管线的深模块，对应用层保留搜索、加载图片、播放器控制、
取消这组小接口，在实现内部独占以下状态：

| 固定区域 | 预算 | 用途 |
| --- | ---: | --- |
| 网络接收区 | 14336 B | 搜索 JSON 与 JPEG 分时复用 |
| JPEG 解码区 | 10240 B | 320x16 RGB565，16 字节对齐 |
| LCD 行缓冲 | 640 B | 320 像素 RGB565 旋转/缩放写屏 |
| 搜索结果固定区 | ≤ 6144 B | 最多 12 条结果，字段超限时按 UTF-8 边界截断 |
| 搜索工作任务栈 | 8192 B | 搜索、图片、播放器操作串行复用 |

接收区与解码区在 JPEG 解码期间必须同时存在，不能做成 union。禁止申请
`320 * 240 * 2 = 153600` 字节的完整 RGB565 帧。

## 4. 实施步骤

### 4.1 固定图片工作区

- 将图片接收区改为 `alignas(16)` 的 14336 字节静态存储；
- 将解码区改为 `alignas(16)` 的 10240 字节静态存储；
- LCD 640 字节行缓冲改为固定存储；
- 删除运行期 `Ensure*Buffer`、`Release*Buffer`、分配重试和额外 512 字节申请余量；
- 启动时记录工作区地址和容量，之后地址必须保持不变。

### 4.2 有界搜索响应

- 搜索 JSON 直接读入同一个 14336 字节网络接收区，不再创建 body 字符串；
- 解析器接受 `std::string_view`，逐项提取字段，不建立完整 cJSON 树；
- 结果固定为最多 12 条，字符串写入固定池；
- 设备仅保存 `media_id`、`title`、`caption`、`image_url`、`start`、`preview_time`；
- 可选文本超过预算时截断，必要字段不足时丢弃该结果，不允许抛异常。

JSON 可以进一步实现为逐条流式解析：HTTP 每收到约 1 KiB 数据就推进词法状态机，在完整
结果对象闭合时写入固定结果区。它可以避免搜索 JSON 占满接收区，但当前不会减少固件的
14 KiB 固定工作集，因为同一接收区还用于 JPEG，而 `esp_new_jpeg` 解码接口要求完整、
连续的 `inbuf + inbuf_len`。只有后端把 JPEG 编码大小硬限制到更小预算，或更换为带输入
回调的增量 JPEG 解码器后，才能真正把该固定区缩到约 1 KiB。

### 4.3 固定任务生命周期

- 搜索、图片和播放器命令使用一个 8192 字节静态工作任务；
- 任务启动后常驻，通过有界命令槽串行处理操作；
- 取消通过 request ID/generation 失效旧结果，不销毁和重建任务；
- 工作任务回调仍通过 `Application::Schedule()` 修改应用状态。

### 4.4 HTTP 适配器加固

- 搜索、图片和播放器控制不再使用 esp-ml307 HTTP 适配器；XiaoZhi MQTT 保持不变；
- 使用 ESP-IDF `esp_http_client_perform()` 在现有静态 worker 中同步执行；
- `HTTP_EVENT_ON_DATA` 直接将每个数据块写入固定接收区，超限立即终止并返回有界错误；
- 客户端内部读缓冲固定为 1024 B，发送缓冲为 512 B；
- HTTP 打开前要求内部堆最大连续块不少于 4 KiB、总空闲不少于 8 KiB；
- 请求结束后同步 cleanup，不存在额外接收任务、被动关闭 event group 竞态或任务内未捕获
  `std::bad_alloc`。

实机验证中，连续约 20 轮快速语音搜索、图片下载与分块解码均成功，稳定态空闲 SRAM
最终回升并稳定在约 30 KiB。期间观察到的一次重启与串口监控关闭/重新打开的时刻完全
重合，是串口 DTR/RTS 控制线触发的硬件复位；监控日志中没有 `Guru Meditation`、abort、
watchdog、OOM 或固件主动重启记录。后续监控应避免切换 DTR/RTS，防止把串口操作造成的
复位误判为应用崩溃。

### 4.5 后端设备图片契约

仅使用 `size=small` 不能保证编码大小或 MCU 对齐尺寸。后端应增加设备规格：

```text
device-small: 固定 320x240 画布，baseline JPEG，宽高为 8 的倍数，<= 14336 B
device-tiny:  固定 160x120 画布，baseline JPEG，宽高为 8 的倍数，<= 8192 B
```

原图先等比缩放，再补边或裁剪到固定画布。固件优先请求 `device-small`，超出接收预算时
只降级一次到 `device-tiny`，之后显示占位提示。90 度旋转在分块写屏阶段完成。

## 5. 错误与降级规则

错误必须区分：网络余量不足、响应超限、无效 JSON、无效 JPEG、JPEG 尺寸不支持、解码
失败和用户取消。禁止把内存申请失败统一显示成 `search image needs a smaller thumbnail`。

搜索仍首先请求 12 条。只有服务响应违反 14336 字节设备预算时，才允许按 6、3、1 条
重试；正常路径不能通过释放解码区换取搜索成功。

## 6. 验收标准

- 单元测试覆盖最大 JSON、12 条结果、超长字段、损坏 JSON、超大/损坏 JPEG、取消和
  快速翻页；
- 搜索管线初始化后，其自有运行路径不再调用大块 `malloc/free`；
- 连续 50 次“ASR -> 搜索 -> 12 张翻页 -> 全屏 -> 播放控制”无重启、无 OOM；
- 第 1 轮到第 50 轮，稳定态空闲内存和最大连续块漂移不超过 1 KiB；
- 每次 HTTP 打开前最大连续块不少于 4 KiB、总空闲内部堆不少于 8 KiB；
- 接收区、解码区和 LCD 行缓冲地址全程不变；
- 构建验证与屏幕、音频、按钮、Wi-Fi、ASR 硬件验证分别报告。

## 7. 不采用的临时方案

- 不通过继续增大 14 KiB 接收区解决协议无上限问题；
- 不依赖 20 次延时重试恢复连续堆；
- 不降低已经验证必要的 24 KiB Opus 栈；
- 不申请完整 RGB565 帧；
- 不切换 ESP-IDF 版本，不通过 Flash 分区调整解决 SRAM 问题。
